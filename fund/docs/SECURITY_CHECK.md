## 3. 已知局限与风险（Phase 2 更新）

1. **内部口令 ≠ IM token 校验（已解决）：** Phase 2 起用户接口改为 IM token（parse_token），旧内部口令头已废除。
2. **安全找回身份核验（已解决基础版，残留局限）：** 已有会话归属（IM token）+ 实名/后 4 位核验 + 双人复核；无短信/邮箱通道时，无法做短信验证码等更强核验——该局限待短信厂商定后补强，当前流程已满足“管理员不能单方面重置、不能接触密码”的底线。
3. **平台结算户偿付能力无熔断（低风险，Phase 2+）：** 平台户余额为净流入清算资金；若某类支出未先有对应流入（如直接支出），CHECK 会拒绝该笔，但系统级“支出总额 ≤ 流入总额”的监控告警尚未建（对账 diff 可发现账实不符，但无实时告警通道）。
4. **Redis 降级模式下的锁语义（低风险，已接受）：** Redis 不可用时降级为纯 DB 保证（FOR UPDATE 串行化仍防超扣），但跨实例的“系统繁忙”协调退化；单实例部署下无实际影响，多实例部署前须复核。
5. **测试夹具与生产密钥分离（已处理）：** 测试代码中的 `test-admin-secret` 与 stub token 前缀仅为测试夹具，不等于生产密钥；生产密钥只在 `fund.env`，两者无交集；`FUND_INTERNAL_SECRET` 已废除，部署时从 `fund.env` 移除。

## 4. Phase 3 新增检查项

1. **红包金额只存在服务端：** IM 自定义消息体只放 packetId，不放金额；领取金额由服务端按包金额入账，客户端请求体无金额字段可供篡改；详情/领取记录仅收发双方可见（第三方 403）。
2. **领取幂等与并发：** 包行 `FOR UPDATE` + 状态 CAS + 领取行 `UNIQUE (packet_id)` 三层防重复领取与超领；同一领取人并发重试收敛到同一条领取记录（Test26）。
3. **准入与密码门禁：** 发包 = 准入 ok + 交易密码；领取 = 准入 ok（不重复验密）；未完成准入时发送/领取均只返回引导、不扣款、不改包状态（Test28/29）。
4. **过期资金闭环：** 24 小时过期 + 扫描/惰性退款 + 退款幂等（状态 CAS + 幂等键），过期包资金必回发送方可用，不滞留冻结（Test31/32）；冻结行异常时领取/退款整笔回滚（Test34）。
5. **已知局限（Phase 3 诚实记录，不冒充已实现）：** ① IM 好友关系校验不在资金服务内——资金服务只校验“领取人 = 包的 receiver_id”，发送方与接收方是否确为 IM 好友须由 chat/App 层在发包前调 OpenIM 好友接口核验（Phase 10/11 落地时接线，届时在网关层强制）；② 退款 IM 业务通知（告知发送方）由 chat 服务/客户端发送，资金服务只返回退款结果，不直接发 IM 消息；③ 单包/单日上限未硬编码，属 Phase 7 风控配置；④ 红包自定义消息类型数值（建议 901）须 Phase 10 核对 SDK 类型区间后定稿。
6. **Phase 4 群红包安全要点：** ① 均分预拆分在服务端建包事务内完成，份金额只存在服务端，IM 消息体只放 packetId，客户端请求体无金额字段可供篡改；② 防超发三层：预拆分份行唯一约束 + 包行锁 + 进度 CAS + 领取行唯一约束（每人限领一次），并发领取测试（Test39）验证恰好 total_count 条领取行；③ 领取人归属：集合非空时只校验包内 receiver 集合，IM 群成员关系校验不在资金服务内，须 Phase 10/11 由 chat/App 层在发包前调 OpenIM 群接口核验并把成员列表传给发包接口（开放包无集合时不校验，文档已如实说明）；④ 过期退款只退剩余金额（total - claimed_amount），冻结行 remaining 与剩余金额不一致时整笔回滚（Test47）；⑤ 发送方领自己的包时只做一次账户更新，避免同人双更新撞乐观锁；⑥ 单包份数上限 1000 与集合上限 1000 为 sanity cap，单包/单日金额上限仍属 Phase 7 风控配置。

## 5. Phase 5 新增检查项

1. **随机预拆分只存在服务端：** 建包时 `crypto/rand` 二倍均值法一次算定并落表，领取时绝不现算现分；IM 自定义消息体只放 packetId，不放金额；客户端请求体无金额字段可供篡改；份行金额领取后不变（Test53 断言份行金额前后一致），事后按份行求和即可审计。
2. **随机算法硬约束落到代码与测试：** 每份 ≥ 1 分、总和严格等于总额、无负数、每份 ≤ 当时剩余金额且为其余份各留 ≥ 1 分（`splitLucky` 注释内含不等式证明）；总额 < 份数时建包拒绝；1000 次拆分专项测试（Test49）与分布抽查（Test50）验证。
3. **手气最佳规则确定且可验：** 金额最大者胜，金额并列时最早领取者胜（领取时间升序、claim_id 升序决胜）；纯函数 `bestLuckyClaim` 单测覆盖并列与同时间决胜（Test54），接口端详情最佳与排名首位一致。
4. **防超发三层（与群普通红包一致）：** 预拆分份行唯一约束 + 包行锁 + 进度 CAS + 领取行唯一约束（每人限领一次），并发领取测试（Test56）验证恰好 total_count 条领取行、金额总和等于总额。
5. **领取人归属与准入：** 集合非空时只校验包内 receiver 集合，IM 群成员关系校验不在资金服务内，须 Phase 10/11 由 chat/App 层在发包前调 OpenIM 群接口核验并把成员列表传给发包接口（开放包无集合时不校验，文档已如实说明）；领取不重复验密但须准入 ok，未完成只引导、不动资金（Test60）。
6. **过期资金闭环：** 24 小时过期 + 扫描/惰性退款 + 退款幂等（状态 CAS + 幂等键），过期包资金必回发送方可用，不滞留冻结（Test58/59）；冻结行异常时领取与过期退款均整笔回滚（Test64）；发送方领自己的包时只做一次账户更新，避免同人双更新撞乐观锁。
7. **已知局限（Phase 5 诚实记录，不冒充已实现）：** ① IM 群成员关系校验不在资金服务内（见第 5 条）；② 退款 IM 业务通知由 chat 服务/客户端发送，资金服务只返回退款结果；③ 单包份数上限 1000 与集合上限 1000 为 sanity cap，单包/单日金额上限属 Phase 7 风控配置；④ 拼手气包与群普通红包表分离，`group_redpacket_*` 与 `group_lucky_redpacket_*` 互不干扰。

## 6. Phase 6 新增检查项

1. **即时到账单状态机：** 全阶段只用一套资金状态机——转账即时到账，与红包即时结算模型一致；待确认模式不做（理由见 API 文档 §9 与迁移 0006 文件头），不留半截待确认分支，避免两套状态机并存的争议路径。
2. **双重记账与同一事务：** 同一 DB 事务、同一 txn_id（type 18）下转出可用 DR / 转入可用 CR 两条分录，金额相等、带符号合计为 0；订单行与账务 txn、分录同事务落库，任一步失败整笔回滚（Test76：收款方冻结时无 type 18 txn、无分录、余额不动）。
3. **并发零超扣：** 涉及账户按 user_id 排序加锁防死锁 + version 条件更新（第二道防线）+ 余额校验；转出方 Redis 辅助锁仅协调，锁被持有回 429；20 并发各转 100（余额 1000）恰好 10 笔成功（Test72）。
4. **幂等：** 成功订单 `UNIQUE (sender_id, idempotency_key)` + 先查后插 + 唯一冲突回查；同一幂等键重复提交返回原订单、不重复扣款（Test71）；失败审计行不带幂等键，事后重发不受阻挡。
5. **门禁与准入：** 转出方 = 准入 ok + 交易密码（`requireTxPassword` 与红包同一门禁）；请求体 user_id 与 token 不一致 403；平台结算户为收款方 403；第三方看不到他人订单详情（Test78/75）。收款方被动入账不设准入关（钱包不存在时同一事务内自动建钱包），收款方准入在其下次主动使用资金时 enforcement——与红包领取须准入的区别已在 API 文档 §9 如实写清；收款方冻结/注销时整笔拒绝（Test74）。
6. **失败语义与纠错：** 结算失败（余额不足 / 收款方冻结 / 注销）只写 status=2 失败审计行，不落账（无 txn、无分录、余额不动）；参数错误、自转、鉴权/准入/密码失败不产生订单行（请求本身无效）；异常纠错只走已有冲正 type 8（不另立 type 19），接收方余额不足时冲正整体失败、原转账不动（Test81）；管理端只查不改，绝不直接改余额、不 UPDATE 订单行改状态。
7. **已知局限（Phase 6 诚实记录，不冒充已实现）：** ① 转出方与收款方是否确为 IM 好友不在资金服务内校验，须 Phase 10/11 由 chat/App 层在发起前核验（与红包同一边界）；② 单笔/单日上限未硬编码，属 Phase 7 风控配置；③ 冲正由转出方本人凭原 txn 发起（现有 `/v1/ledger/reverse` 接口），管理端不代发起、不直接改账；④ 转账 IM 业务通知（如“收到转账”提醒）由 chat 服务/客户端发送，资金服务只返回订单结果，不直接发 IM 消息；⑤ UI 落地在 Phase 10/11。

## 7. Phase 7 新增检查项

1. **管理端绝不直接改余额：** 调整单执行走统一双重记账事务（txn type 19，`ref_type='admin_adjustment'`），
   与红包/转账同一模型：同一事务内记账 + 单据状态 CAS + 审计行，任一步失败整笔回滚；代码中无管理端
   `UPDATE wallet_account SET balance` 直写路径（调整执行只在事务内按分录方向更新余额并带 version 条件）。
   注意：type 19 是管理员调整专用——转账冲正仍复用 type 8（Phase 6 定稿不变），两者不得混淆。
2. **双人复核无单人直通：** 全部调整单统一双人复核（不设金额阈值单人直通）；第一复核只记录、不动余额
   （Test86）；第二复核与记账同一事务（行锁 + 状态重查），并发第二复核只有一个能执行；
   同一人两次复核拒绝（Test89）；减额超余额时执行回滚、第二复核人不落单（Test89）。
3. **调整单只查不改、执行后不可撤销：** 无修改接口；已执行/已拒绝单据的 approve/reject 均 400（Test88）；
   纠错只走反向调整单（须注明已执行原单号且方向相反，建单时校验，Test88）；原单行与已执行 txn 永不改写。
4. **交易密码管理禁看哈希：** 管理查询 SQL 不 SELECT `password_hash` 列；响应结构无哈希字段；

   本阶段行为，防止把“配置已保存”误读为“限额已全面生效”；限额变更记审计（`admin_risk_limit_update`）。
8. **敏感操作审计：** 调整单创建/复核/执行/拒绝、提现审核、限额变更一律记 `wallet_audit_log`（append-only，
   detail 已脱敏）；管理端审计日志只读查询接口（`GET /v1/admin/audit-logs`）供核查（Test93）。
9. **越权隔离：** 全部管理接口无密钥/错密钥/普通用户 token 一律 401；双人复核类缺 `X-Admin-ID` 一律 401（Test92）。
10. **已知局限（Phase 7 诚实记录，不冒充已实现）：** ① admin-front 源码缺口仍在（见 API 文档 §12 前置核查），
    本阶段交付 API + 接线规约，不交付前端 UI、不伪造 UI；② 单日上限与红包限额未接入执行，留 Phase 8/9；
    ③ 调整单创建人不受限（可担任第一复核人），但一人无法完成两步——若未来要求创建人与复核人完全分离，
    须另立规则并在创建时校验；④ 提现审核通过后无打款动作，打款与回填在 Phase 9；⑤ UI 落地在源码补齐后，
    按 API 文档 §12.8 接线。

## 8. Phase 8 新增检查项

1. **回调验签是唯一门禁：** 回调接口无用户鉴权，签名验签是唯一入口——验签失败 401、订单与资金均不动
   （Test97）；签名覆盖订单号、渠道单号、金额、状态四字段（canonical 载荷，字段顺序固定），
   任一字段被篡改即验签失败（Test97 篡改金额用例）；签名原文与密钥绝不进日志（handler 只记订单号）。
2. **签名 ≠ 金额一致：** 签名只能证明回调体未被篡改，不能证明金额与订单一致——回调处理在验签通过后
   仍做金额一致性校验，不一致 400 并记审计，订单不动、资金不动（Test99）；两层校验缺一不可已写入 API 文档 §13.2。
3. **回调入账同一事务：** 订单行锁 + 状态 CAS + 账务入账 + 审计同一事务（Test96 分录合计 0、type 20）；
   并发回调由订单行锁串行化，第二笔按幂等重放处理，不重复入账（Test98）；渠道单号唯一索引防串单（第二道防线）。
4. **非法流转与退款安全：** 合法流转只有待支付 → 已支付、待支付 → 已失败、已支付 → 已退款，
   其余一律 409（Test100/103）；退款余额不足时整笔回滚、订单与余额不动，另起短事务记审计
   （Test102，口径同转账失败审计行：审计行不落账、只留痕）；钱包冻结/注销时回调整笔回滚并记审计。
5. **Mock 环境隔离三层：** ① 开关控制注册（`FUND_MOCK_PAYMENT=1` 才注册 mock 回调精确路由，开关关闭回 404，
   Test106）；② 开关开启要求 HMAC 密钥非空，否则服务拒绝启动（`ConfigFromEnv`）；③ 测试全部在
   `xianliao_fund_test` 库跑，生产库只验证空表与健康检查；Mock 与真实订单以 `channel` 字段区分，管理端可过滤。
6. **真实渠道零信任默认：** 创建侧拒绝非 mock 渠道（400 `CHANNEL_NOT_AVAILABLE`，Test95）；
   真实渠道回调入口恒回 501（验签骨架 `UnconfiguredVerifier`，Test106），绝不入账、绝不把回调体当支付成功处理；
   真实商户密钥、证书一律不进仓库（只进生产 `fund.env` / 证书文件），签约前置清单见 API 文档 §13.4。
7. **无虚假成功页：** 客户端创建订单、页面操作、交易密码均不能直接增加余额——入账唯一路径是渠道验签通过的
   回调事务（`POST /v1/ledger/income` 为 Phase 1 内部 primitive 口径，真实充值不走该口）；创建接口不设准入/
   交易密码门禁的理由已在 API 文档 §13.1 写清（建单本身不产生资金变动）。
8. **已知局限（Phase 8 诚实记录，不冒充已实现）：** ① 真实支付宝/微信验签器未落地（只有骨架 + 501），
   须商户签约后按 §13.4 清单接入并先跑官方沙箱；② 渠道手续费现为 0（`fee_cents=0`，`actual=amount`），
   费率政策待签约后定；③ 渠道对账（渠道账单 vs 订单 + 分录的日终对账任务）未建，留签约后与验签器同批落地；
   ④ 充值创建不查准入（见第 7 条理由），若未来要求充值前完成准入，须另立规则并在创建时接 `requireAdmission`。

## 9. Phase 9 新增检查项

1. **提交守卫顺序与“只引导、不扣款”：** 准入引导优先（非 ok 只返回引导、不扣款、不建单，Test111）→
   验交易密码（Test110）→ 方式归属（本人正常方式，否则 404，Test112）→ 金额上下限与频率限制
   （Test113/115）→ 余额校验（Test109）；任一步失败均不产生资金变动、不建成功订单行。
2. **冻结与解冻的同一事务性：** 提交冻结（type 22）、拒绝解冻（type 23）、打款扣减（type 24）、
   失败退款解冻（type 25）均为订单状态 + 账务 + 冻结行 + 审计的同一 DB 事务；冻结行 remaining
   必须等于订单总额（金额 + 手续费）否则整笔回滚（与红包异常防护同口径）；全部 type 22–25 txn
   分录合计为 0（Test108/116/117/118/123）。
3. **审核与打款分离：** 审核通过（双人复核）只改状态、不产生资金变动、不打款（Test117 第一复核后
   余额与状态不动）；打款是独立的“处理中 → 回填凭证 → 成功”步骤，凭证缺失时确认被拒绝（400），
   成功单必须有回单号（数据库 CHECK 约束兜底）；审核通过后页面与接口必须明示“未打款”。
4. **人工打款唯一路径与垫付禁令：** 无商户资质时唯一打款路径为对公账户/企业网银手工转账 + 回填凭证；
   严禁个人号垫付为常规流程（文档 §14.3 与代码注释均明确写出）；自动打款只留 501 骨架
   （Test119），不连真实渠道端点、不写真实商户密钥，签约前置清单见 API 文档 §14.5。
5. **失效方式不打款：** 打款确认前复核方式仍为本人正常方式；流程中解绑方式时确认被拒绝（400），
   操作员走失败 → 退款逃生通道，资金全额返回用户（Test124）。
6. **非法流转拒绝：** 合法流转只有 0→1、0→2、1→3、3→4、3→5、5→6，其余一律拒绝
   （新入口 409、Phase 7 旧入口保持 400，Test119）；订单状态机与资金变动一一对应，无“状态已成功但款未动”
   或“款已动但状态未变”的半笔。
7. **手续费与限额的服务端计算：** 手续费与实际到账金额全部服务端按配置重算（试算接口仅展示用，
   不作为提交依据）；`actual ≤ 0` 时拒绝提交；配置变更走管理端（变更记审计），客户端不得指定手续费。
8. **权限隔离：** 提现详情/列表仅本人可见（他人 404，不透露归属，Test121）；管理端流转接口须
   `X-Admin-Secret` + `X-Admin-ID`（操作员可审计）；方式非本人与不存在同一 404 码，不透露他人方式存在性。
9. **已知局限（Phase 9 诚实记录，不冒充已实现）：** ① 自动打款未落地（只有 501 骨架），须商户签约后按
   §14.5 清单接入并先跑官方沙箱；② 手续费的收入确认不在本账务口径内（订单行 `fee_cents` 为唯一事实记录，
   未来手续费收入报表以订单行汇总为准，不得另起账本）；③ 日终人工打款对账（银行回单 vs 成功单）为
   线下流程，未建自动对账任务，留签约自动打款后与验签器同批落地；④ 频率限制按数据库当日统计，
   跨时区部署时以数据库服务器当日为准，运营须按此时区口径设定限额。
